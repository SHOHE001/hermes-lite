## A. ログから見つかった未修正の問題

### A-1. 週次 goals-nudge が systemd 経由で一度も発火していない（critical）

場所: `systemd/claude-agent@.timer`, `jobs/goals-nudge/`（欠落しているのは `~/.config/systemd/user/claude-agent@goals-nudge.timer.d/schedule.conf`）

`claude-agent@.timer` は「既定はスケジュールなし、ジョブごとに drop-in で `OnCalendar=` を上書きする」設計だが、goals-nudge だけその drop-in が作られていない。結果 systemd はタイマーの読み込み自体を拒否し（`Loaded: bad-setting`）、`list-timers --all` にも現れない。mail-digest / mail-watch / jobwatch-review には drop-in と `timers.target.wants` エントリが両方あり、goals-nudge だけ両方欠落している。

発生実績: journal に `Jul 19 22:48:34` の `Timer unit lacks value setting. Refusing.`、監査時（`Aug 02 09:10` / `09:32`）にも同一エラーを再確認。`logs/goals-nudge/` は 2026-07-03 15:17 の手動実行1件のみで以降更新なし。`docs/jobs-goals-nudge.md` が謳う「毎週日曜 20:00 JST に Discord へ nudge」は一度も届いていない。

直し方:

```bash
mkdir -p ~/.config/systemd/user/claude-agent@goals-nudge.timer.d
printf '[Timer]\nOnCalendar=Sun *-*-* 20:00:00\n' > ~/.config/systemd/user/claude-agent@goals-nudge.timer.d/schedule.conf
systemctl --user daemon-reload
systemctl --user enable --now claude-agent@goals-nudge.timer
```

再発防止として、timer drop-in の有無を jobwatch の定期監視項目に加える。

### A-2. mail-watch の FAIL 通知が原因を落とし、Discord に `(no stderr)` だけが届いた（high）

場所: `bin/run-claude.sh:222-231`

`ERR_SNIPPET` の選定が `_has_error_line -eq 1 || "$RESULT_TEXT" == ERROR:*` → `[[ -s "$ERR_LOG" ]]` の2分岐しかない。claude CLI 自身が返すエラー文字列は `ERROR:` プレフィックスを持たないため両方の条件が外れ、stderr も空だと `${ERR_SNIPPET:-(no stderr)}` が発火する。ラッパーは常に `exit 0` で終わる設計（235行）なので、systemd 側の `list-units --failed` でも拾えない。

発生実績: `logs/mail-watch/20260801-200004.json` と `20260801-220004.json` の両方が `{"is_error":true, "result":"Failed to authenticate: OAuth session expired and could not be refreshed"}`。対応する `.stderr` は両方 0 バイト。journal は `[run-claude] FAIL exit=1 is_error=true` のみ。OAuth 失効という直せる原因が、通知からも journal からも読み取れなかったのが 8/1 の 20:00 と 22:00 の2回。

直し方: `bin/run-claude.sh:225` の前に「`IS_ERROR == "true"` かつ `RESULT_TEXT` 非空ならフォールバックとして採用する」分岐を追加する。`ERROR:` プレフィックスの有無に関係なく claude の返した本文が通知に載る。

### A-3. skill 自動生成ループが 6/20 の稼働開始から一度も成功していない（high）

場所: `skills-loop/bin/on-stop.py:75-104`（`_build_prompt`）, `skills-loop/prompts/skill-review.md:13`

`_build_prompt()` が「## 会話 (直前ターン)」に元の対話の生テキストを先に置き、「## あなたへの指示」を末尾に後置している。子 `claude -p` は末尾のメタ指示より先に埋め込まれた会話を「今答えるべき依頼」と誤認し、レビューではなく会話の継続応答を返す。

発生実績: `skills-loop/state/runs/on-stop-*.json` は全810件。うち `claude_exit_code==0` は464件だが、stdout が JSON パース可能だったのは19件のみで、その19件すべてがレビューを実行せず直前会話の続きを返していた。`prompts/skill-review.md` が要求するフォールバック文言「Nothing to save.」は0件。`~/.claude/skills/hermes-lite/.usage.json` は現在も `{}`、`.archive/` は空、agent_created な skill はゼロ。

別の失敗モードも同時に出ている。464件中445件は exit_code==0 なのに stdout が完全に空。さらに346件は exit_code==1 で完全失敗（07/02〜07/17 は100%失敗）。プロンプト構造とは別種で、原因は未特定。

直し方: レビュー指示を先頭に移すか、会話部分を「参照専用の過去ログであり応答対象ではない」と明示的に区切る。あるいは `--append-system-prompt` 側にレビュー指示を分離する。exit0/stdout空 と exit1 の大量発生は別途切り分けが必要。

### A-4. on-stop.py の子 claude が無制限権限で走り、実際にシステムファイルを編集した（high）

場所: `skills-loop/bin/on-stop.py:107-127`（`_run_claude`）

cmd は `[CLAUDE_BIN, "-p", "--output-format", "json", "--add-dir", str(skill_io.HERMES_LITE_ROOT), prompt]` のみで、`--allowedTools` / `--disallowedTools` / `--permission-mode` が一切ない（`bin/run-claude.sh` は `--permission-mode default` と `lib/disallowed-tools.txt` を必ず付与しているのと対照的）。さらに `~/.claude/settings.json` のグローバル `permissions.allow` に `Edit(*)` `Write(*)` `Bash(*)`、`defaultMode` が `auto`。

加えて `_run_claude` が `cwd=str(Path.home())` を指定するため、プロジェクト側 `.claude/settings.json` の PreToolUse ガードも子プロセスには効かない。実質 `$HOME` 全域に対して Bash・Edit・Write が無制限。

発生実績: `skills-loop/state/runs/on-stop-20260719T153112Z.json` の result に「二重通知の修正を適用しました。`notify-pc.sh` に skill review の子 Claude を判定するガードを1行追加し…」とあり、実際に `~/.claude/hooks/notify-pc.sh` を編集していた。その5行目 `[ "${HERMES_SKILL_REVIEW_RUNNING:-0}" = "1" ] && exit 0` は現在も本番に残っている。実害は軽微だったが、権限自体は毎回無制限のまま。

直し方: `_run_claude` に `--allowedTools`（Read/Edit/Write を `~/.claude/skills/hermes-lite/` 配下限定）を付けるか、`bin/run-claude.sh` と同じ `--disallowed-tools` + `--permission-mode default` を適用する。`cwd` をホームではなく hermes-lite ルートにすればプロジェクトの PreToolUse ガードも効く。

## B. critical

### B-1. approvals_executor の Discord 通知にリトライが無い

場所: `lib/approvals_executor.py:256-274`（`notify_discord`）／対比: `lib/notify.sh:29-32`

`notify_discord` は `urllib.request.urlopen(req, timeout=10)` を1回呼ぶだけで、例外は stderr WARN を出して握りつぶす。一方 `lib/notify.sh` は `c5d66d5`（2026-08-01）で `curl -fsS --retry 3 --retry-delay 2 --retry-connrefused --retry-all-errors --max-time 20` を獲得済み。そのコミットメッセージは「2026-07-08, 07-09 に DNS の一時失敗で投稿が落ち、しかも落ちたのがジョブ失敗を知らせる FAIL 通知そのものだったため障害が二重に沈黙した」と明記しており、同じ webhook URL に対して実際に失敗した実績がある。Python 側は `a69fe14` の初期実装から一度も変更されていない。

この関数は、calendar.create の副作用検証で異常を検知したときの `failed_after_side_effect` 警告を送る唯一の経路（`lib/approvals_executor.py:300,317-321,335-339,358-362,375-380`）。承認処理は `systemd-run --user --no-block` の使い捨て unit で走るため、この1回の POST が失敗すると stderr はその場限りの journal にしか残らず、Calendar に重複イベントができてもユーザーは気づけない。

緊急度の注記: 承認ゲートは drop-in で有効化済み・bot も稼働中だが、`var/approvals.sqlite` は0行、mtime は 2026-06-26 のセットアップ時刻のままで5週間以上使われていない。ただし実機の claude CLI (v2.1.187) は tool_use evidence を返さないため、使われれば必ずこの警告経路を通る。

直し方: `notify_discord` の urlopen を2〜3回の指数バックオフ付きリトライにする。または `lib/notify.sh` を subprocess 経由で呼ぶ形に寄せて実装を一本化する。

## D. medium

### D-1. `/clear` がロックを取らず、実行中の応答完了時に削除済みセッションが復活する

場所: `gateway/discord/bot.py:403-421`（slash ルート、ロック無し）, `292-300`（`_handle` は `locks[lock_key]` を取得）, `264-265`（`store.set`）

on_message の slash 分岐は `reply = await asyncio.to_thread(slash_commands.dispatch, stripped, ctx)` をロック取得なしで即実行し、`clear_handler` は `store.delete(ctx.scope_key)` だけを行う。一方 `_handle()` は `async with locks[lock_key]` の中で `_run_with_resume` を回し、その末尾で `store.set(scope_key, initial_result.session_id)` を実行する。

長時間発話（本番 `.env` は `TIMEOUT_SEC=900`）の最中に `/clear` を送ると、削除は即座に成功して「✅ セッションをクリアしました」と返るのに、裏で走っていた `_handle()` が完了時に旧 lineage の session_id を書き戻すため、次の発話が旧セッションを resume する。

直し方: slash dispatch（少なくとも `/clear`）も `locks[scope_key]` を取得してから実行する。あるいはクリア時刻を記録し、`store.set` 側でそれより古い書き込みを破棄する。

### D-2. 同一ジョブの多重起動を防ぐロックが無い

場所: `bin/run-claude.sh`（全体に flock/lockfile なし）, `jobs/mail-watch/prompt.md` 手順6, `jobs/mail-digest/prompt.md` 手順3

`run-claude.sh` / `jobs/*/job.env` / `systemd/*.{service,timer}` を `grep -n "flock\|lockfile"` してもヒットがない。mail-watch の手順6 は `notified.json` / `pending.json` を Read →（LLM が組み立て）→ Write する非アトミックな更新。手動実行と定期実行が近接して重なると、後から Write した側が先の Write を丸ごと上書きし、保留キューへの追記消失や同一 threadId の二重即時通知が起こりうる。

実際 `logs/mail-watch/cost.csv` には 2h 間隔の定期実行の間に手動実行 `20260801-161503` が挟まった実績がある（このときは1時間45分空いていたため衝突していない）。

直し方: `run-claude.sh` 冒頭でジョブ単位の `flock -n "$LOG_DIR/.lock"` を取り、取得できなければスキップして次回タイマーに委ねる。

### D-3. `lib/switchbot.py` の `_request` にリトライが無い

場所: `lib/switchbot.py:113-143`

`urlrequest.urlopen` を1回呼び、`HTTPError` / `URLError` を即 `SwitchBotError` に変換して raise する。呼び出し経路は実在し、`gateway/discord/claude_runner.py:124` が `Bash(python3 lib/switchbot.py:*)` を許可ツールに登録、`systemd/switchbot-action@.service` は `Type=oneshot`・`Restart=` 未設定で `bin/sb-schedule` から定期実行される。同種の一時的ネットワーク不調（DNS）は notify.sh 側で 2026-07-08/07-09 に実発生している。SwitchBot 固有の障害ログは見つかっておらず、この経路での実発生は未確認。

`systemd/switchbot-action@.service:19-20` は `lib/notify.sh`（リトライ済み）経由で失敗を通知するため、失敗そのものは確実に届く。問題は瞬間的な障害でも機器操作がリトライされず手動対応が必要になる点。

直し方: `_request` の urlopen に指数バックオフ付き2〜3回リトライを追加する。4xx の `HTTPError` は除外し、`URLError` / タイムアウト系のみをリトライ対象にする。

### D-4. `session_log.read_jsonl` が「valid JSON だが dict でない行」で落ちる

場所: `skills-loop/lib/session_log.py:8-22`, `62-82`, `85-94`; `skills-loop/bin/usage-tracker.py:39-57`

docstring は「壊れた行は黙ってスキップ。」と謳うが、実装は `json.JSONDecodeError` しか捕捉していない。監査中に `[1,2,3]` を含む jsonl を作って `read_jsonl → extract_last_turn / list_loaded_skills` を呼び、`AttributeError: 'list' object has no attribute 'get'` を実測で再現済み。

`usage-tracker.py` の jsonl ループにはファイル単位の try/except が無いため、`~/.claude/projects` 配下の825ファイルのうち1つでもこの形の行を含めば、cron 2:30 の集計が全 skill 分まとめてクラッシュし、curator は古い usage_store で週次判定を続行する。現時点で該当行は0件だが、A-3 が直って skill が作られ始めると露出する。

直し方: `read_jsonl` 内で `isinstance(obj, dict)` を満たさない行を破棄する。`usage-tracker.py` の per-file ループも try/except で個別ファイルの失敗を隔離する。

### D-5. 最終応答の送信ループに例外ハンドリングが無い

場所: `gateway/discord/bot.py:314-325`, `455`

同じ関数内の notice_text 送信は `try: await message.channel.send(notice_text) except discord.HTTPException: log.warning(...)` で保護されているのに、直後の `for chunk in _split_for_discord(result.text): await message.channel.send(chunk)` には保護が一切ない。`on_message` 側の `await _handle(message)` にも try/except が無いため、送信例外は discord.py のイベントディスパッチが最終的に握りつぶす。プロセスは落ちないが `hermes-lite.discord.bot` ロガーには何も残らず、journalctl をロガー名で監視する運用では応答欠落を検知できない。

直し方: 同じ send ループを `try/except Exception` で囲み、`log.exception` で記録した上でユーザーに簡易エラーを返す。

### D-6. mail-watch フィードバックのロックがチャンネル単位で共有ファイルの排他になっていない

場所: `gateway/discord/bot.py:433`, `gateway/discord/mail_rules_handler.py:98-151`

ロックキーは `f"mailrules:{message.channel.id}"` とチャンネル単位だが、`_rules_path()` は `MAIL_WATCH_RULES_PATH` 固定の単一ファイルを指し、`_backup()` / `_run_claude()` / `_validate()` はどのチャンネルから呼ばれても同じ rules.md を対象にする。`config.py` の `MAIL_WATCH_CHANNEL_IDS: list[int]` は複数 ID を想定した型なので、2つ目を追加した時点で backup→`claude -p` Edit→validate が競合しうる（現在は ID 1件のみのため未発現）。

### D-7. `ALLOWED_TOOLS` の未クォート展開でグロブ展開が起こりうる

### D-8. 承認 executor の秘密鍵 denylist が SwitchBot 系を含んでいない

### D-9. `claude -p` タイムアウト時、孫プロセスが孤児として残る

場所: `gateway/discord/claude_runner.py:101-115,187-220`; `gateway/discord/mail_rules_handler.py:51-54`

`subprocess.run(cmd, ..., timeout=TIMEOUT_SEC, ...)` は `start_new_session` / `process_group` を指定しておらず、リポジトリ全体を grep しても `setsid` / `start_new_session` / `killpg` / `preexec_fn` は一切使われていない。CPython の実装上、TimeoutExpired 時に kill されるのは Popen 直下の claude プロセスだけ。

`DISALLOWED_TOOLS` が禁じているのは `Bash(rm *)` `Bash(sudo *)` `Bash(git push*)` `Bash(git reset*)` の4パターンのみで、一般の Bash は通る。本番 `.env` は `HERMES_DISCORD_TIMEOUT_SEC="900"`。900秒でハングした場合、claude が Bash 経由で起動した孫プロセスは init に reparent され、常駐サーバー上に回収されないまま蓄積する。

直し方: `subprocess.Popen(..., start_new_session=True)` でプロセスグループを分離し、TimeoutExpired 時に `os.killpg(os.getpgid(proc.pid), signal.SIGKILL)` でグループごと終了させる。

### D-10. empty_history の noop にクールダウンが無い

場所: `gateway/discord/compaction.py:569-587`（empty_history 分岐）, `129-142`（cooldown 実装）

`older, recent = _extract_history(...)` で `not older` のとき `CompactionResult(status="noop", ...)` を返すが、`mark_failed()` を呼ばないため `_failed_recently` dict に登録されず cooldown が効かない。size トリガー成立（jsonl >= 480,000 byte）かつ user 発話が keep_turns（既定10）以下の状態に入ると、以後そのセッションへの全メッセージで jsonl 全体を1行ずつ読み直し続け、jsonl は伸びる一方なのでコストが単調増加する。C-1 とセットで発生する。

直し方: empty_history 分岐にも軽い cooldown（数分程度）を設ける。
